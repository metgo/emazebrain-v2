# ADR 0004 — Login with mandatory staff MFA, and a hash-chained audit log

- Status: Accepted
- Date: 2026-10-22
- Design doc: §6, §9.3, §9.9, §10.5, §11.2

## Login

- **Better Auth 1.7.7**, self-hosted inside the API. Email + password (12–128 characters) now; passkeys and Google/Microsoft OIDC later through plugins.
- **TOTP two-factor is mandatory for staff.** A signed-in user without it gets `403 mfa_required` on every `/v1` route. With it on, a password alone never creates a session; the TOTP code (or a backup code) does.
- Rate limiting on (100 requests / 15 min per client IP, stricter built-in limits on two-factor endpoints). A test proves repeated wrong codes hit `429`.
- **Codes are single-use.** A before-hook atomically claims (user, code) in `auth.totp_claim` (migration 0004); the same code is refused for 120 s, which covers its ±1-step validity. Added 2026-10-23.
- Auth tables live in schema **`auth`**, which the app role `emb_app` cannot read. Password hashes, sessions and TOTP secrets never reach RLS queries. TOTP secrets are stored encrypted with `AUTH_SECRET`.
- Auth ids are **UUIDv7** generated by the API. A hook creates the matching `app.app_user` row with the same id, which is the `app.user_id` that RLS sees.
- The schema is a committed, reviewed migration (`0003_auth.sql`) generated by `apps/api/scripts/generate-auth-migration.ts`, not created at runtime.

## Audit log

- `app.audit_event` is append-only (trigger) and readable under RLS: users see their own actions, clinic managers their clinic's.
- **Writes** to `patient`, `patient_care_team`, `consent`, `membership` and `clinic` are logged by trigger with the **names** of changed columns only, never values. Archiving (`deleted_at`) is logged as `delete`.
- **Reads** are logged by the API through `app.record_audit()`: `list` for the patient list, `view` for one patient. The actor always comes from the session (`app.user_id`), never from the caller, and every row carries the request id.
- The app role cannot insert, update or delete audit rows; `record_audit()` is the only way in.
- Rows are **hash-chained**: each hash covers the previous one. `app.verify_audit_chain()` (not callable by the app) returns any row whose chain breaks; a test edits history with triggers disabled and the check catches it.
- One global chain serialises appends through a lock on `audit_chain_head`. Fine at MVP volume; moves to one chain per monthly partition when the table is partitioned (§10.2).

## Open

- The API's service connection and the trigger functions' owner must be a role that can `SET ROLE emb_app` and bypass RLS for the owner's own definer functions. Confirm the role layout on Amazon RDS together with ADR 0002's open item.
- A daily anchor of the chain head to S3 Object Lock (§10.5) comes with the infrastructure work.
